ARBI V28 — PODMIANA CAŁEGO KODU

1. Zrób kopię repozytorium arbi na GitHubie: Code > Download ZIP.
2. Rozpakuj arbi_v28_rebuild.zip na komputerze.
3. Na GitHubie otwórz repo arbi > Add file > Upload files.
4. Przeciągnij do okna Upload ZAWARTOŚĆ rozpakowanego folderu (folder app, docs, tests oraz scanner.py, scan_runtime.py, requirements.txt, README.md).
   Wgraj kod do katalogu głównego repozytorium, nie do dodatkowego folderu arbi_v28_rebuild.
5. Kliknij Commit changes. Dane i historia powiadomień nie są dołączone do paczki, więc zachowasz obecne data/state.json i docs/data/latest.json.
6. Workflow podmień OSOBNO: otwórz .github/workflows/surebet.yml > Edit; usuń cały kod i wklej treść surebet_v28.txt.
7. Podmień tak samo .github/workflows/watchdog.yml treścią watchdog_v28.txt. Jeśli pliku nie ma, utwórz go przez Add file > Create new file.
7a. DODAJ też .github/workflows/heartbeat.yml (jest już w paczce). To on sam wyzwala Surebet Scanner co około 2 minuty. Nie potrzebuje cron-job.org ani włączonego komputera.
8. Settings > Pages > Build and deployment > Source: GitHub Actions.
9. Zachowaj dotychczasowe sekrety SITE_PASSWORD, TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID oraz OneSignal. Nie wklejaj ich do kodu.
10. Actions: anuluj uruchomienia starej wersji, które nadal trwają. Następnie Surebet Scanner > Run workflow > main, tylko raz.
11. Nowy run nosi nazwę Arbi v28. Po publikacji odśwież stronę Ctrl+F5. Pod statusem zobaczysz czas ostatniej próby oraz jej wynik.

CO SIĘ ZMIENIŁO
- Czas wykrywania sportów jest ograniczony; kolejność sportów zmienia się w następnych cyklach.
- Odczyt jednego wydarzenia ma limit i nie blokuje wszystkich kolejnych.
- Skaner uruchamia się pod kontrolą procesu nadzorującego (scan_runtime.py), który kończy zawieszoną próbę.
- Nieudany skan publikuje aktualny status błędu, a data ostatniego udanego skanu pozostaje prawdziwa.
- W razie błędu znikają stare okazje surebet/value; podgląd katalogu pozostaje dostępny jako dane historyczne.
- Strona pobiera wynik z pierwszego działającego endpointu, nie czeka bez końca na drugi i nie cofa się do starszej wersji danych.
- Brak świeżych danych kończy run błędem dopiero PO opublikowaniu statusu diagnostycznego.

WYWOŁANIA CO 2 MINUTY
Nowy workflow heartbeat.yml uruchamia okno wywołań i wysyła repository_dispatch `surebet_scan` do surebet.yml co 120 sekund. GitHubowy cron samego skanera pozostaje awaryjny.
Automatyczne skany zapisują świeży docs/data/latest.json bezpośrednio do main, a strona sprawdza go co 3 sekundy. Dzięki temu nie trzeba czekać na pełny deploy Pages po każdym skanie.
Pełny deploy GitHub Pages jest wykonywany przy ręcznym Run workflow — zrób go raz po wgraniu tej paczki.
Jeśli skan trwa dłużej niż 2 minuty, GitHub nie uruchomi dwóch kopii równocześnie; następne wywołanie poczeka. Dlatego nie da się obiecać nowego kompletu kursów dokładnie co 120 sekund.
Ta paczka nie zapewnia dostępu do wszystkich bukmacherów. Działanie źródeł musi zostać potwierdzone w Twoich Actions.

JEŚLI RUN JEST CZERWONY
Otwórz pierwszy czerwony krok. Jeśli to „Zgłoś błąd skanera po publikacji diagnostyki”, log scanner-debug zawiera scanner.log i debug. Pobierz go przez sekcję Artifacts i prześlij tutaj. Jeśli czerwony jest inny krok, prześlij jego komunikat.
